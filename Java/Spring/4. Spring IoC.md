# 4. Spring IoC — Inversion of Control

## Core Principle

IoC means the *control of object creation and dependency wiring is inverted* — handed from application code to the framework. You define *what* you need; Spring decides *how and when* to create it.

## Without IoC (tight coupling)

```java
class OrderService {
    private PaymentService ps = new PaymentService();
}
// OrderService is locked to a specific PaymentService implementation. Can't swap, can't mock.
```

## With IoC

```java
class OrderService {
    @Autowired PaymentService ps;
}
// Spring injects whichever PaymentService implementation exists in the context.
// Swap implementations by changing config only.
```

## IoC Container Responsibilities

| Responsibility | Description |
|---|---|
| Instantiation | Creates bean objects (using constructors or factory methods) |
| Configuration | Reads metadata: XML, annotations (@Component, @Bean), or Java config |
| Wiring | Resolves & injects dependencies automatically |
| Lifecycle | Calls @PostConstruct, @PreDestroy; manages scope (singleton, prototype…) |
| AOP proxying | Wraps beans with proxies for @Transactional, @Cacheable, etc. |

## Configuration Styles (all equivalent)

| Style | Example | Notes |
|---|---|---|
| XML | `<bean id="svc" class="…ServiceImpl"/>` | Legacy, but still valid |
| Annotation | `@Component` / `@Service` / `@Repository` on classes | Most common |
| Java Config | `@Configuration` class with `@Bean` methods | Full type safety |

## IoC vs DI — The Distinction

IoC is the *design principle* (give up control). Dependency Injection is the *mechanism* Spring uses to implement IoC — it injects dependencies into your objects rather than having them look up or create their own.
